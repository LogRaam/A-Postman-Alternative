Le problème

Quand l'IA écrit le code, la première chose qui se perd, c'est de savoir ce qui existe déjà

Une IA ne garde aucune mémoire d'une séance à l'autre. Elle ne connaît que ce qu'elle lit. Rien ne la pousse à chercher si un concept existe déjà, alors elle le recrée, proprement, sous un autre nom. Chaque classe est correcte; c'est le concept qui s'éparpille.

Sur ce projet même, en une soirée, trois règles ont été réécrites à côté de l'originale : la règle « une ligne compte si elle est cochée et nommée », la règle « un nom vide prend une valeur par défaut », et la copie d'une ligne clé-valeur. Aucune revue de code ligne par ligne ne les aurait vues; elles étaient chacune dans un fichier différent.

Un fichier de règles pour l'IA est un conseil, et il vieillit. Une documentation écrite à la main pourrit en silence, et on continue de s'y fier.

La méthode

Des « maps » générées depuis le code, et un test qui échoue quand elles ne sont plus vraies

Une map est une vue du système (inventaire des modules, dépendances, règles promises par les tests, format des fichiers d'export) générée à partir du code source et commitée comme un fichier ordinaire. Un test la régénère et la compare à la copie commitée. Si le code a bougé et pas la map, la suite de tests échoue. Le test est le déclencheur : la map ne peut pas vieillir.

Chaque changement produit donc deux diffs : celui du code, et celui de la map, qui dit ce que le changement veut dire pour la structure. Pour un réviseur, c'est souvent le seul qui vaut la peine d'être lu.

Deux sortes de tests

Certaines maps informent, d'autres bloquent

Les confondre, c'est la façon la plus rapide de transformer la méthode en paperasse. Une map qui informe accepte ce que dit le code; une vérification qui bloque refuse, et régénérer ne la fait pas passer.

Informe

Lire, régénérer, commiter

  • Inventaire : chaque module et chaque fonction, avec sa ligne de doc
  • Dépendances : qui importe qui, cycles en premier
  • Règles : chaque nom de test, la spécification vivante
  • Identifiants HTML partagés entre le gabarit et le code
  • Le fichier livré est bien construit depuis le code actuel
Bloque : contrats

Des promesses faites à l'extérieur

  • Un champ d'export publié ne peut pas disparaître ni se restreindre
  • Un champ ajouté après une publication doit être optionnel
  • Les clés de stockage du navigateur ne changent jamais
Bloque : cliquets

Des chiffres qui ne peuvent que baisser

  • Modules pris dans un cycle d'import : 0
  • Imports du cœur logique vers l'interface : 0
  • Fichiers de 300 lignes et plus : 0
  • Identifiants cherchés par le code mais absents du gabarit : 0

Une dérive mesurée, puis corrigée

Le fichier principal, commit après commit

Sans la map, cette croissance passe inaperçue : chaque ajout est raisonnable en soi. Avec elle, la tendance se lit à chaque commit, et la correction se vérifie.

Pour l'architecture d'entreprise

Ce que ce mode de travail garantit

TraçabilitéChaque changement est un commit qui dit ce qui a été ajouté et ce que la structure a montré. L'historique se relit comme un journal de décisions.
Spécification vivanteLa map des règles liste les 83 comportements promis par les tests, dont 8 vérifiés dans un vrai navigateur. Un comportement qui change sans test qui change est un test manquant, et on le sait.
Contrats tenusLe format des fichiers d'export et les clés de stockage sont des promesses faites aux utilisateurs. Les casser fait échouer la suite, même si quelqu'un régénère tout.
Dérive bornéeCycles, couches et taille des fichiers sont des cliquets : ils peuvent s'améliorer, jamais se dégrader sans une décision écrite.
Revue possibleOn révise le diff des maps avant celui du code. Une revue d'architecture tient en quelques lignes par changement.
Aucune dépendanceLe produit est un seul fichier HTML, sous licence MIT. Rien à installer, rien à mettre à jour, aucune bibliothèque tierce à surveiller.

Les limites, dites franchement

Ce que la méthode ne règle pas

  • Le même concept sous deux noms différents. La map les met côte à côte; c'est le jugement humain qui décide qu'ils n'en font qu'un.
  • Le même modèle écrit le code et ses tests. Les tests risquent de confirmer ce que fait le code plutôt que ce qu'il devrait faire. La relecture humaine des règles reste le contrepoids.
  • Ce qu'aucune map ne regarde. Les champs ajoutés comme obligatoires en sont l'exemple : vus seulement à la relecture, puis transformés en vérification bloquante.
  • Les limites d'une page web. Une API qui refuse les requêtes venant d'une page (CORS) ne répond pas; certains en-têtes ne peuvent pas être fixés. Les jetons et mots de passe sont gardés en clair dans le navigateur et dans les exports.
  • Les tests d'interface tournent dans Chrome ou Edge; Firefox, le thème sombre et les petits écrans restent à vérifier.

Déroulé de la démo · 10 minutes

Ce qu'on montre en direct

  1. Ouvrir l'application. 1 min

    Double-cliquer sur dist/postman-alternative.html. Envoyer un GET vers https://httpbin.org/get.

  2. Un environnement, une collection. 2 min

    Créer « Dev » avec baseUrl = https://httpbin.org, taper {{baseUrl}}/get : l'aperçu montre l'adresse réelle. Ctrl+S pour l'enregistrer dans une collection.

  3. Montrer une map. 2 min

    Ouvrir docs/maps/dependencies.md sur GitHub : aucun cycle, le cœur n'importe jamais l'interface. Puis rules.md : la spécification se lit en français simple.

    https://github.com/LogRaam/A-Postman-Alternative/tree/main/docs/maps
  4. Lire un commit. 2 min

    Ouvrir le commit 347cfa6 : son message dit ce que les maps ont montré avant d'écrire une ligne de code.

  5. Casser un contrat, en direct. 3 min

    Dans une copie du dépôt, figer le format comme s'il était publié, retirer un champ d'export, régénérer : la commande refuse et nomme le champ. Régénérer ne contourne pas un contrat.

    npm run update-maps -- --record-released
    npm run update-maps
